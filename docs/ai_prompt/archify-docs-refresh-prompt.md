# docs/archify 갱신 프롬프트

archify 아키텍처 다이어그램 + 구조체/함수 목적 정리 + 중복·미사용 코드
점검을 한 번에 요청할 때 쓰는 프롬프트. 2026-08-15에 naverBlog 저장소에서
실제로 이 작업을 해본 뒤, 겪은 시행착오를 반영해 정리함.

## 프롬프트

```
docs/archify 디렉터리를 최신 상태로 갱신해줘. 없으면 새로 만들어줘.

1. archify 스킬로 현재 코드베이스 전체(모든 internal/ 패키지, cmd/, 외부 연동
   포함)를 반영한 아키텍처 다이어그램을 그려서
   docs/archify/<repo>-architecture.json / .html로 저장하고,
   showcase 품질 검증(validate → deliver)까지 통과시켜줘.
   - 기존 파일이 있으면 그 파일을 베이스로 갱신(디렉터리/좌표 재사용),
     없으면 새로 설계해줘.

2. 소스 코드 전체를 실제로 훑어서(grep/read, 추측 금지) 모든 exported
   구조체·함수의 목적을 패키지별로 정리한 문서
   (docs/archify/struct-function-reference.md)를 작성해줘.
   각 항목에 파일:라인 근거를 남기고, "확인함" / "추론" 구분해줘.

3. 같은 문서 안에 아래 두 섹션을 별도로 리스트업해줘:
   - 중복 코드: 여러 파일/패키지에 동일하거나 거의 동일한 로직이 반복되는
     곳. 실제로 grep/read로 바이트 단위까지 대조한 것만 올리고, 파일:라인을
     인용해줘.
   - 미사용/죽은 코드: 어디서도 호출되지 않는 exported 함수·구조체·설정
     필드. 정적분석 도구(staticcheck/deadcode 등)가 없으면 grep으로 호출부를
     직접 대조하고, 그 방법론적 한계를 문서에 명시해줘.

4. docs/archify 안에 예전 비교/설계 문서가 있으면 전면 재작성하지 말고,
   상단에 "이 문서는 <날짜> 스냅샷, 최신 정보는 <새 문서>를 참고"라는
   배너만 추가하고 나머지는 역사적 기록으로 남겨줘.

5. 커밋은 하지 말고 결과만 보여줘.
```

## 각 항목을 이렇게 쓴 이유

- **"기존 파일 있으면 베이스로, 없으면 새로"** — 처음부터 새로 배치를
  설계하면 archify 다이어그램 좌표(노드 위치·연결선 경로) 잡는 데 시간이
  많이 든다. 기존 좌표를 재사용할 수 있으면 훨씬 빠르다.
- **"추측 금지" / "확인 vs 추론 구분"** — 글로벌 CLAUDE.md 원칙과 동일.
  중복·미사용 목록은 특히 잘못 판단하면 신뢰가 깨지는 항목이라 명시적으로
  강조하는 게 좋다.
- **"방법론적 한계 명시"** — 정적분석 도구가 없는 환경이면 grep 수작업으로
  확인하게 되는데, 이걸 숨기지 않고 문서에 남겨야 나중에 신뢰도를 판단할
  수 있다.
- **"배너만 추가"** — 오래된 비교문서를 매번 전면 재작성하면 비용이 크다.
  스냅샷 배너 + 새 문서 링크 방식이 훨씬 효율적이다.
- **"커밋하지 말고"** — 요청 없이 임의로 커밋하지 않는다는 기존 규칙과
  일치시킴.
