# 토스 출시 관점 구현 점검 및 다음 작업

작성일: 2026-09-10

## 오늘 점검 요약

현재 프로젝트는 Three.js 기반의 모바일 맞고 프로토타입이다. 기본 48장 덱, 10/10/8/20 초기 배분, 손패와 덱 카드의 바닥패 매칭, 2장 선택, 기본 점수 계산, 고/스톱, 설사 감지, CPU 턴, 결과 오버레이까지 연결되어 있다.

확인 명령:

- `npm test`: 3개 테스트 파일, 17개 테스트 통과
- `npm run build`: TypeScript와 Vite 프로덕션 빌드 통과
- 프로덕션 번들: 약 557KB, Vite의 500KB 초과 경고 발생
- 작업 트리 점검: 기존 코드 변경 없음

## 출시 차단 우선순위 — P0

### 1. 한글 인코딩과 HTML 문자열 복구

`index.html`, `src/main.ts`, `src/game/rules.ts` 등에 한글이 `移대뱶`, `愿?`와 같은 깨진 문자열로 저장되어 있다. 점수 패널 문자열에는 `</strong>`, `</li>` 등 HTML 닫기 태그가 깨진 흔적도 있다. 현재 테스트 일부도 정상 문자가 아닌 깨진 문자열을 기대하므로 이 결함을 검출하지 못한다.

할 일:

- 관련 파일을 UTF-8 기준으로 복구
- 화면 제목, 상태 메시지, 점수 설명, 결과 메시지 전수 확인
- 테스트 기대 문자열을 정상 한글로 변경
- 실제 브라우저에서 시작 화면부터 결과 화면까지 확인

### 2. 앱인토스 실행·패키징 구조 확인

현재 `package.json`에는 Vite, Three.js, Vitest만 있고 앱인토스 WebView SDK 및 앱 설정 파일이 없다. 토스 앱 내부 실행을 목표로 한다면 앱인토스용 초기화, 빌드, 앱 정보, 실행 환경을 별도로 연결하고 샌드박스에서 확인해야 한다.

할 일:

- 앱인토스 WebView 연동 방식 결정
- `@apps-in-toss/web-framework`와 프로젝트 설정 도입 여부 확인
- 토스 샌드박스에서 진입·종료·뒤로가기·복귀 테스트
- 게임물 등급 심의 및 출시 제출 체크리스트 확인

### 3. 출시 룰 범위 확정

현재 구현은 기본 매칭과 기본 점수 중심이다. 폭탄, 흔들기, 쪽, 따닥, 뻑, 나가리, 피박, 광박, 멍따, 고박 등 일반 맞고에서 기대할 수 있는 특수 룰은 아직 구현 범위에서 확인되지 않는다.

할 일:

- 간소화 맞고로 출시할지 일반 맞고로 출시할지 결정
- 간소화 버전이면 미지원 룰을 안내
- 일반 맞고면 특수 룰을 `RuleProfile` 또는 `RuleOptions`로 분리해 추가
- 룰별 결정 테이블과 테스트 fixture 작성

## 출시 품질 우선순위 — P1

### 4. 반복 플레이 안정성

재시작 시 `Game.clearAllCards()`는 카드 Mesh를 장면에서 제거하지만 geometry와 material을 dispose하지 않는다. 반복 플레이가 길어지면 모바일 WebGL 메모리 사용량이 누적될 수 있다.

할 일:

- `CardMesh.dispose()` 추가
- geometry, material, 사용하지 않는 texture 정리
- 10판 이상 연속 재시작 테스트
- WebGL context 손실 시 오류 안내와 복구 경로 추가

### 5. 점수 상태와 UI의 단일화

설사 처리의 `transferPi()`는 점수를 변경하지만 일반 카드 획득 이벤트와 같은 UI 갱신 경로가 아니다. 또한 상단 UI는 쌍피를 물리적인 1장으로 세고 점수 패널은 2피로 계산한다.

할 일:

- 점수·피 수·획득 카드 수의 데이터 모델을 분리
- 모든 점수 변경을 하나의 이벤트 또는 selector 경로로 통합
- 설사 후 플레이어와 CPU 점수 즉시 갱신
- 화면에 “패 장수”와 “피 값”을 구분해서 표시

### 6. 백그라운드·복귀·저장

현재 `visibilitychange`, `pagehide`, `pageshow` 처리와 진행 중인 판 저장이 없다. 토스 안에서 다른 화면으로 이동했다가 돌아오는 상황을 고려해야 한다.

할 일:

- 백그라운드 전환 시 입력과 애니메이션 일시정지
- 복귀 시 상태 복원 또는 안전한 재시작
- 진행 상태 저장 포맷과 버전 정의
- 중복 실행·복귀 중 입력 방지

### 7. 실제 모바일 E2E 검증

현재 검증은 게임 규칙 단위 테스트 중심이며, 브라우저에서 터치로 한 판을 끝내는 E2E 테스트가 없다.

필수 시나리오:

- 정상 매칭과 무매칭
- 손패 선택과 덱 카드 선택
- 2장 선택 모달
- 고/스톱 반복
- CPU STOP과 결과 화면
- 재시작 중복 입력
- 작은 세로 화면에서 손패·바닥패·하단 UI 겹침
- 백그라운드 전환 후 복귀

## UX 및 완성도 — P2

- 첫 실행 튜토리얼과 룰 설명
- 한 번 탭하면 즉시 내는 대신 선택 후 확정하는 실수 방지 흐름
- 현재 턴, 덱 잔량, 예상 점수의 명확한 표시
- 획득 카드 전체 보기
- 광·고도리·고/스톱 결과 연출
- 효과음·진동·접근성 라벨
- 저사양 기기용 그림자·픽셀 비율 최적화
- Three.js 번들 분할 및 카드 이미지 메모리 최적화
- 토스 게임센터 리더보드 연동 검토

## 권장 작업 순서

1. 한글·HTML 문자열 전수 복구
2. 브라우저에서 기본 한 판과 결과 화면 재검증
3. 앱인토스 WebView 빌드·샌드박스 연결
4. 룰 범위 확정 및 미지원 룰 안내
5. 카드 리소스 dispose와 점수 UI 갱신 통합
6. 백그라운드 복귀와 저장 처리
7. 모바일 E2E 테스트 작성
8. 특수 룰, 사운드, 리더보드 등 확장

## 판단

현재 상태는 기본 게임 루프가 동작하는 프로토타입으로는 충분하다. 토스 출시 후보로 올리기 전에는 문자열 인코딩, 앱인토스 실행 구조, 룰 범위, 반복 플레이 안정성, 모바일 E2E 검증을 우선 완료해야 한다.
