# 2인 이상 멀티플레이어 단계별 구현 계획

## 1. 목표와 우선순위

목표는 여러 게임을 한 번에 완성하는 것이 아니라, 서로 다른 기기에서 최소 2명이 실제로 한 게임을 끝까지 진행할 수 있는 수직 슬라이스를 먼저 확보하는 것이다.

우선순위는 다음과 같다.

1. 방 생성·입장·퇴장과 사용자 식별
2. 두 기기의 턴·행동·결과 동기화
3. 서버 권위형 규칙 판정과 재접속 복구
4. 3인 맞고와 4인 이상 관전자·광팔기 확장
5. 포커·블랙잭·윷놀이·사다리·뱀주사위·슬롯 추가
6. UI·연출·BGM·SFX·리플레이·통계 고도화
7. 유료아이템 검토 및 구현

유료아이템은 초기 게임성 검증 이후의 후순위 항목으로 둔다. 초기 범위에서는 게임머니 구매, 환전, 유저 간 양도, 승률에 영향을 주는 상품을 구현하지 않는다. 추후 장식형 아이템을 추가할 수 있도록 아이템 소유권과 결제 연동 지점만 확장 가능하게 둔다.

## 2. 권장 통신·판정 구조

WebRTC를 핵심 게임 통신으로 사용하지 않는다. 카드·주사위·슬롯 결과와 잔액은 클라이언트가 결정하면 안 되므로 관리형 백엔드가 상태와 결과를 권위적으로 관리한다.

```text
각 기기
  ├─ 방/행동 요청
  └─ 서버 결과 렌더링
          ↓
관리형 백엔드
  ├─ 인증·방·Presence
  ├─ Realtime Broadcast
  ├─ 규칙·턴·난수 판정
  ├─ 이벤트 로그·스냅샷
  └─ 재접속·탈주·정산 처리
```

초기 후보는 Supabase Realtime + Edge Function/Database Function이다. Firebase도 대체 후보로 남기되, 실제 구현은 한 제공자로 고정하여 중복 작업을 피한다.

## 3. 단계별 구현 순서

### Phase 0 — 규칙 엔진 경계 고정

- [x] `GameState`, `GameAction`, `GameEvent`, `GameResult` 공통 타입 정의
- [ ] 게임별 규칙 판정과 Three.js/UI 렌더링 분리
- [x] `roomId`, `gameId`, `roundId`, `sequence`, `actorId` 공통 필드 확정
- [x] 서버가 결과를 결정하고 클라이언트는 요청·표시만 담당하는 계약 작성
- [ ] 48장 고유 카드 invariant와 기존 CPU 흐름 보존

검증: 브라우저 없이 규칙 엔진 테스트로 정상 행동·중복 행동·잘못된 턴·재전송을 검증한다.

### Phase 1 — 2인 최소 수직 슬라이스

첫 번째 실제 게임은 맞고 전체 규칙이 아니라, 구현·검증이 쉬운 공통 턴제 샘플로 시작한다. 카드 게임을 먼저 선택할 경우에도 특수룰을 한꺼번에 넣지 않고 기본 카드 선택과 점수 정산까지를 목표로 한다.

- [ ] 방 생성 및 짧은 방 코드 입장
- [ ] 2개 기기에서 서로 다른 플레이어 식별
- [ ] ready/start/turn/action/result 흐름 구현
- [ ] 한 기기의 행동이 다른 기기에 순서대로 반영
- [ ] 서버에서 잘못된 턴·중복 요청·잘못된 action 거부
- [ ] 정상 종료와 한 명 이탈 시 종료·승패 처리
- [ ] 재접속 시 최신 snapshot 복구
- [ ] 점수와 종료 결과를 두 기기에 동일하게 표시

완료 기준: 서로 다른 네트워크의 실제 기기 2대가 방에 들어와 한 판을 시작하고, 행동·턴·결과가 일치한 상태로 종료된다.

### Phase 2 — 맞고 3인 및 4인 이상 확장

- [ ] `players[]`, `activeSeats[]`, `spectators[]` 기반 상태로 확장
- [ ] 3인 손패·바닥패·덱 분배와 턴 순환 검증
- [ ] 쌍피·특수룰·GO/STOP·점수 산정 서버 판정
- [ ] 4번째 이상 참가자 처리: 관전자/광팔기/빠지기 정책 분리
- [ ] 탈주·방장 이탈·재접속·타임아웃 처리
- [ ] 3~4대 실기기 E2E 검증

### Phase 3 — 공통 게임 플랫폼 확장

공통 방·턴·이벤트·로그·재접속 계층을 재사용하고, 게임별 규칙 모듈만 추가한다.

- [ ] 윷놀이: 윷 결과·말 이동·잡기·추가 턴
- [ ] 뱀주사위: 주사위·이동·사다리·뱀·종료
- [ ] 사다리: 참가자·선택지·결과 공개와 재현 로그
- [ ] 블랙잭: 덱·딜러·hit/stand·정산
- [ ] 포커: 베팅 라운드·fold/call/raise·승패
- [ ] 슬롯: 서버 난수·확률표·배당·결과 로그

게임 추가 순서는 윷놀이/뱀주사위처럼 단순한 턴제 게임을 먼저 두고, 포커·블랙잭·슬롯은 검증 가능한 난수·정산·운영 로그를 확보한 뒤 진행한다.

### Phase 4 — 표현·운영 고도화

- [ ] 방 목록·친구 초대·관전자 UI
- [ ] 서버 이벤트와 애니메이션의 분리
- [ ] 실제 BGM/SFX·mute·백그라운드 복귀·reduced motion
- [ ] 결과 공유·리플레이·신고·문의용 게임 로그
- [ ] 지연·재접속·오류 상태의 사용자 안내
- [ ] 동시 접속·메시지량·비용 모니터링

### Phase 5 — 유료아이템(후순위)

- [ ] 장식형 아이템 범위 확정
- [ ] 게임 결과·판돈·승률에 영향을 주지 않는지 검증
- [ ] 아이템 catalog·소유권·지급 멱등성 설계
- [ ] 앱인토스 결제·복구·환불 상태 연동 검토
- [ ] 게임머니 판매·환전·양도는 별도 정책/법률 검토 전 구현하지 않음

## 4. 사용자 확인이 필요한 결정

초기 구현은 아래 기본값으로 진행할 수 있다.

- 게임머니: 무료 가상 단위, 현금·토스포인트와 무관
- 매칭: 방 코드 초대 우선, 랜덤 매칭은 후순위
- 로그인: 토스 사용자 식별 기반, 게스트는 초기 실험 범위에서 제한
- 첫 수직 슬라이스: 2인 턴제 게임
- 백엔드: Supabase 후보로 POC 후 확정
- 유료아이템: 후순위, 장식형 가능성만 열어둠

다음 결정만 사용자 확인이 필요하다.

- 첫 수직 슬라이스를 맞고 기본판으로 할지, 별도 단순 턴제 게임으로 할지
- 최종적으로 게스트 플레이를 허용할지
- 랜덤 매칭을 출시 범위에 포함할지

## 5. 완료 판정

각 Phase는 다음을 모두 만족해야 다음 단계로 이동한다.

- 규칙 엔진 자동 테스트 통과
- `npm test`와 `npm run build` 통과
- 필요한 경우 `npm run test:browser` 통과
- 클라이언트 2개 이상에서 동일한 sequence·결과 확인
- 48장 고유 카드 invariant 유지
- 재접속·중복 요청·이탈자 처리 확인
- 사용자 확인이 필요한 정책을 임의로 확정하지 않음
