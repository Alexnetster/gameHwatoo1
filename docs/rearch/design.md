새로운 모바일 화투 게임 프로토타입을 만들어줘.

목표는 토스 미니앱(Apps in Toss)에 올릴 수 있는 모바일 Web 게임이다.

기술적으로는 Three.js를 사용하고, 한국에서 일반적으로 익숙한 2인 맞고의 플레이 흐름을 기준으로 한다.

단, 기존 상용 맞고 게임의 UI, 디자인, 그래픽, 소리, 코드, 특정 서비스 명칭을 그대로 복제하지 않는다.

게임 규칙과 사용자가 익숙하게 느끼는 플레이 방식만 참고하고, 전체 디자인과 구현은 독자적으로 만든다.

# 1. 개발 목표

첫 번째 버전은 실제로 플레이 가능한 MVP를 완성한다.

우선순위:

1. 2인 맞고 한 판을 처음부터 끝까지 플레이 가능
2. Three.js 기반 화투패 표현
3. 카드 선택 및 이동 애니메이션
4. 점수 계산
5. 고/스톱 선택
6. 승패 처리
7. 다시하기
8. 모바일 터치 UX
9. 토스 미니앱에서 실행 가능한 구조

멀티플레이 네트워크 기능은 첫 버전에서는 만들지 않는다.

Player 1 = 실제 사용자
Player 2 = CPU

로 구현한다.

그러나 게임 엔진은 이후 아래 형태로 확장 가능해야 한다.

* Player vs CPU
* Player vs Player
* 3인 고스톱
* 온라인 매칭

즉 게임 규칙 코드와 화면 코드를 분리한다.

# 4. 그래픽 방향

완전한 3D 게임처럼 만들지 않는다.

목표:

"실제 테이블 위 화투를 손으로 치는 느낌을 가진 2.5D 모바일 게임"

카드는 PlaneGeometry 또는 얇은 BoxGeometry를 이용한다.

카드에 약간의:

* 그림자
* 깊이
* 회전
* 원근
* 움직임

을 적용한다.

카드를 선택하면:

1. 카드가 약간 위로 올라온다.
2. 선택 카드가 강조된다.
3. 터치하면 중앙으로 이동한다.
4. 바닥패와 맞으면 두 카드가 살짝 모인다.
5. 획득패 영역으로 이동한다.

애니메이션은 과장하지 않는다.

빠르고 손맛 있게 만든다.

목표 애니메이션 시간:

150~350ms

# 5. 화투 카드

한국 화투 48장을 사용한다.

12개월 × 4장 구조를 데이터로 정의한다.

각 카드에는 최소한 다음 데이터를 가진다.

interface HwatuCard {
id: string;
month: number;
category: 'gwang' | 'animal' | 'ribbon' | 'junk';
subType?: string;
image: string;
}

예:

{
id: "jan-gwang",
month: 1,
category: "gwang",
image: "/cards/jan-gwang.webp"
}

게임 규칙에서 이미지 파일명이나 렌더링 구조에 의존하면 안 된다.

# 6. 카드 리소스

프로토타입용 카드 이미지를 별도 assets 디렉터리에 관리한다.

예:

/public/cards/
01_01.webp
01_02.webp
...
12_04.webp

실제 상용 게임의 카드 이미지를 복사하지 않는다.

화투 특유의 월별 특징은 유지하되 독자적인 카드 디자인을 사용할 수 있도록 구조화한다.

카드 이미지가 아직 없으면 개발 중에는 임시 Placeholder를 생성한다.

Placeholder에는:

* 월 번호
* 카드 종류
* 간단한 도형

만 표시한다.

게임 로직을 이미지 제작과 분리한다.

# 7. 기본 게임 방식

첫 버전은 2인 맞고 규칙을 기준으로 한다.

초기 분배:

각 플레이어 손패:
10장

바닥:
8장

남은 카드:
더미

턴 진행:

1. 플레이어가 손패 1장을 선택
2. 바닥에 같은 월 카드가 있는지 확인
3. 규칙에 따라 카드 획득
4. 더미에서 카드 1장을 뒤집음
5. 다시 같은 월 카드 확인
6. 획득 처리
7. 점수 계산
8. 턴 종료
9. 다음 플레이어

# 8. 같은 월 카드 처리

바닥에 같은 월 카드가 없는 경우:

카드를 바닥에 놓는다.

1장 있는 경우:

둘을 획득한다.

2장 있는 경우:

사용자가 어느 카드를 먹을지 선택한다.

CPU는 내부 전략에 따라 선택한다.

3장 있는 경우:

해당 월 카드들을 획득한다.

가능하면 일반적인 맞고 플레이 방식과 비슷하게 구현한다.

# 9. 획득패 분류

획득한 카드는 자동으로 아래 그룹으로 정리한다.

광

열끗

띠

피

획득패 영역에서는 카드 전체를 크게 보여주지 않는다.

겹쳐서 정렬한다.

예:

광  [패][패]

열  [패][패][패]

띠  [패][패][패]

피  [패][패][패][패][패]

# 10. 점수 시스템

점수 계산은 UI 코드와 완전히 분리한다.

별도 모듈:

src/game/scoring.ts

형태로 만든다.

최소 지원:

* 광

* 삼광

* 비삼광

* 사광

* 오광

* 열끗

* 고도리

* 띠

* 홍단

* 청단

* 초단

* 피

* 쌍피

일반적인 한국 맞고 규칙을 기준으로 구현한다.

지역이나 서비스마다 규칙이 달라질 수 있는 부분은 상수 또는 RuleConfig로 분리한다.

예:

interface RuleConfig {
goScoreThreshold: number;
shakeEnabled: boolean;
bombEnabled: boolean;
doublePiEnabled: boolean;
}

규칙을 코드에 하드코딩하지 않는다.

# 11. 고 / 스톱

사용자가 승리 가능한 점수에 도달하면 게임을 잠시 정지한다.

화면 중앙에:

"고 할까요?"

버튼:

[고]

[스톱]

표시.

고:

게임 계속.

고 횟수 증가.

스톱:

즉시 게임 종료.

최종 점수와 승자를 보여준다.

# 12. 특수 규칙

첫 프로토타입에서는 구조를 만들어 두되 지나치게 복잡하게 만들지 않는다.

가능하면 다음 규칙을 지원한다.

* 쪽
* 따닥
* 싹쓸이
* 폭탄
* 흔들기
* 피박
* 광박
* 고박

하지만 핵심 게임이 먼저 정상 동작해야 한다.

개발 우선순위:

기본 매칭
→ 점수
→ 고/스톱
→ 특수 규칙

순으로 구현한다.

특수 규칙 때문에 기본 게임 구조가 복잡해지면 기능을 분리한다.

# 13. CPU

첫 버전 CPU는 복잡한 AI를 사용하지 않는다.

규칙 기반으로 만든다.

우선순위 예:

1. 당장 점수를 얻는 카드
2. 광 획득
3. 고도리 가능 카드
4. 단 완성 가능 카드
5. 피 획득
6. 상대에게 좋은 패를 주지 않는 선택
7. 랜덤

CPU 판단 로직:

src/game/cpu.ts

화면 코드와 분리한다.

CPU는 약 500~900ms 생각하는 것처럼 지연 후 플레이한다.

너무 즉시 움직이지 않는다.

# 16. 중요 설계 원칙

게임 규칙이 화면을 직접 조작하지 않는다.

잘못된 예:

playCard() 안에서

scene.add()
element.innerHTML
camera.position

등을 직접 호출하지 않는다.

게임 엔진은:

GAME_EVENT_CARD_CAPTURED

GAME_EVENT_SCORE_CHANGED

같은 이벤트만 발생시킨다.

렌더링 레이어가 이벤트를 받아 애니메이션을 실행한다.

# 19. 터치

모바일 터치를 최우선으로 한다.

Raycaster를 사용해서 카드 터치를 감지한다.

카드 선택 영역은 실제 카드보다 약간 크게 잡는다.

연속 터치나 빠른 터치 때문에 중복 입력되지 않도록 inputLock을 구현한다.

애니메이션 진행 중에는 필요한 입력만 허용한다.

# 22. 토스 미니앱 고려사항

토스 앱 안의 WebView에서 실행되는 모바일 게임을 전제로 한다.

따라서:

* 빠른 초기 로딩
* 작은 번들
* 모바일 GPU 부하 최소화
* 메모리 누수 방지
* 과도한 Particle 사용 금지
* 고해상도 Texture 남용 금지
* WebGL Context 관리
* 화면 회전 대응
* Safe Area 대응

을 고려한다.

최초 화면까지 가능한 빠르게 보여준다.

Heavy Asset은 최초 실행에 전부 로딩하지 않는다.

카드 이미지와 필요한 리소스만 우선 로딩한다.

# 23. Three.js 성능 기준

가능하면:

1 Renderer

1 Main Scene

OrthographicCamera 또는 약한 PerspectiveCamera

를 사용한다.

조명도 최소화한다.

예:

AmbientLight
DirectionalLight

정도로 충분하다.

실시간 고품질 그림자는 사용하지 않는다.

카드 그림자는:

* 간단한 Plane
* CSS
* Sprite

중 가벼운 방법을 선택한다.

PixelRatio는 무조건 devicePixelRatio 전체를 사용하지 않는다.

예:

renderer.setPixelRatio(
Math.min(window.devicePixelRatio, 2)
);

저사양 모바일에서도 플레이 가능한 것을 우선한다.

# 25. 디자인

토스 앱 자체 UI를 복제하지 않는다.

별도의 게임 브랜드를 가진다.

전체 스타일:

* 깔끔한 모바일 게임
* 현대적인 한국 카드게임
* 과도한 카지노 느낌 금지
* 실제 도박 게임 같은 연출 금지
* 명확한 카드 가독성
* 큰 터치 영역
* 최소한의 텍스트

배경은 전통적인 녹색 고스톱판을 그대로 복제하지 말고 좀 더 현대적으로 재해석한다.

# 27. 디버그 모드

개발 중에는 화면 한쪽에 Debug Panel을 제공한다.

표시:

Turn

Current Player

Deck Count

Player Hand Count

CPU Hand Count

Table Card Count

Player Score

CPU Score

Game Phase

디버그 모드는:

const DEBUG = true

로 켜고 끌 수 있게 한다.

# 28. 재현 가능한 게임

버그 재현을 위해 랜덤 시드를 지원한다.

예:

new Game({
seed: 12345
});

동일한 seed에서는 동일한 카드 분배가 가능해야 한다.

이는 화투 규칙 테스트에 중요하다.

# 29. 테스트

다음 항목은 반드시 확인한다.

카드 총합이 항상 48장인지

중복 카드가 존재하지 않는지

손패 + 바닥패 + 더미 + 획득패 = 항상 48장인지

턴이 중복 진행되지 않는지

같은 카드를 두 번 획득하지 않는지

점수가 정확히 계산되는지

게임 종료 후 입력이 차단되는지

CPU가 없는 카드를 선택하지 않는지

카드 애니메이션 도중 상태가 꼬이지 않는지

# 30. 첫 결과물

처음부터 거대한 완성본을 만들려고 하지 말고,

"실제로 한 판 플레이 가능한 최소 게임"

을 먼저 완성한다.

최초 결과물에서 반드시 가능해야 하는 것:

* 앱 실행
* 새 게임
* 카드 배분
* 내 카드 선택
* 같은 월 카드 먹기
* 더미 카드 뒤집기
* CPU 플레이
* 점수 계산
* 고/스톱
* 승패 결정
* 다시하기

임시 그래픽이어도 괜찮다.

게임 로직이 정확한 것이 그래픽보다 우선이다.

# 31. 구현 시 중요 사항

코드를 작성하기 전에 현재 프로젝트 구조를 먼저 확인한다.

기존 코드가 있다면 전체를 새로 만들지 않는다.

기존 소스를 최대한 유지하면서 필요한 부분만 수정한다.

관련 없는 기존 기능은 삭제하지 않는다.

기존 함수의 변경으로 해결할 수 있으면 불필요한 새 추상화를 만들지 않는다.

새 함수가 기존 코드와 직접 관련이 적다면 가능한 파일 하단이나 별도 모듈에 배치한다.

수정 후 반드시:

* TypeScript 문법
* import 경로
* 타입 오류
* Three.js API 사용
* unused 변수
* build 오류

를 다시 확인한다.

npm run build

가 성공하는 상태까지 만든다.

# 32. 최종 기준

이 프로젝트의 목표는

"Three.js 기술 데모"

가 아니다.

사용자가 실행하자마자 별도 설명 없이 화투를 한 판 칠 수 있는 게임이어야 한다.

Three.js는 게임 경험을 자연스럽게 만드는 수단으로만 사용한다.

가장 중요한 것은:

1. 맞고에 익숙한 사람이 바로 이해할 수 있는 진행
2. 정확한 카드 상태
3. 정확한 점수 계산
4. 빠른 터치 반응
5. 짧고 자연스러운 카드 애니메이션
6. 모바일 WebView 안정성

이다.

먼저 현재 프로젝트 파일을 분석한 뒤 구현을 시작한다.

파일이 비어 있다면 위 구조를 기준으로 최소 프로젝트를 생성한다.

최종적으로 실제 실행 가능한 코드를 제공하고, 수정 후 build까지 검증한다.



# 화면 구성 및 UX 기준

첫 번째 프로토타입에서는 기존 모바일 맞고 게임에서 널리 사용되는 화면 구성과 UX 패턴을 적극적으로 참고한다.

목적은 처음부터 새로운 UX를 만드는 것이 아니라,

"기존 맞고 UX를 기준선으로 구현한 뒤 실제 플레이를 통해 개선점과 차별점을 찾는 것"

이다.

단, 특정 상용 게임 하나의 화면을 픽셀 단위로 복제하지 않는다.

여러 모바일 맞고 게임에서 공통적으로 사용되는 정보 구조와 인터랙션 패턴을 기준으로 한다.

# 1. 기본 화면 구조

모바일 세로 화면 기준.

화면 위쪽:

* 상대 프로필 영역
* 상대 점수
* 상대 획득패
* 상대 손패

화면 중앙:

* 게임 진행 메시지
* 바닥패
* 뒤집을 카드 더미
* 현재 턴 표시

화면 아래쪽:

* 내 획득패
* 내 점수
* 내 손패
* 메뉴 / 설정 버튼

전체적으로 기존 모바일 맞고 사용자가 별도 설명 없이 바로 이해할 수 있어야 한다.

# 2. 플레이 화면 UX

카드 선택 방식도 기존 맞고 게임에서 익숙한 방식으로 구현한다.

내 손패를 터치하면:

1. 카드가 살짝 올라온다.
2. 선택 상태가 표시된다.
3. 다시 터치하거나 명확한 선택 동작을 하면 카드를 낸다.

단순한 상황에서는 한 번 터치만으로 바로 낼 수도 있도록 UX를 비교 가능하게 설계한다.

바닥에 같은 월 카드가 두 장 있을 경우:

* 먹을 수 있는 카드들을 강조
* 사용자가 원하는 카드를 직접 터치
* 선택 후 즉시 획득 처리

사용자가 현재 무엇을 해야 하는지 항상 시각적으로 알 수 있어야 한다.

# 3. 바닥패 구성

화면 중앙에 바닥패를 배치한다.

카드가 무작위 위치에 흩어지는 방식보다는 모바일 가독성을 우선한다.

기본:

* 월별 매칭을 쉽게 찾을 수 있음
* 카드가 서로 지나치게 겹치지 않음
* 최대 카드 수가 늘어나도 화면 밖으로 나가지 않음

기존 맞고 게임처럼 약간 자연스럽게 흩어진 느낌은 주되 실제 선택 영역은 명확하게 유지한다.

# 4. 손패 UX

내 손패는 화면 하단에 가장 크게 보여준다.

10장 기준으로 한 화면에 들어와야 한다.

카드가 많을 경우 일부 겹침을 허용한다.

선택한 카드는:

* 위로 이동
* 약간 확대
* 그림자 또는 밝기 변화

중 하나 이상을 사용한다.

현재 낼 수 없는 카드라는 개념이 없는 경우 불필요하게 카드를 비활성화하지 않는다.

# 5. 상대 손패

상대 카드의 앞면은 보이지 않는다.

카드 뒷면을 일정 간격으로 겹쳐서 표시한다.

남은 카드 수를 직관적으로 파악할 수 있어야 한다.

CPU가 카드를 낼 때:

상대 손패
→ 중앙
→ 바닥패

순서가 눈에 보이도록 애니메이션한다.

# 6. 카드 획득 UX

카드를 먹었을 때 즉시 획득패 영역으로 순간 이동시키지 않는다.

바닥에서 잠깐 매칭 상태를 보여준 뒤:

바닥패
→ 플레이어 방향
→ 획득패 영역

으로 이동한다.

사용자가

"무슨 카드를 냈고 무엇을 먹었는지"

눈으로 따라갈 수 있어야 한다.

# 7. 뒤집기 UX

손패 플레이가 끝난 후 더미에서 카드 한 장을 뒤집는다.

더미:

화면 중앙 한쪽에 배치.

뒤집을 때:

1. 카드가 더미에서 나온다.
2. 짧게 뒤집힌다.
3. 중앙에 표시된다.
4. 매칭 여부를 보여준다.
5. 획득 또는 바닥 배치된다.

전체 과정은 너무 느리지 않게 한다.

# 8. 점수 UX

점수는 항상 화면에서 확인 가능해야 한다.

점수가 발생하면:

기존 점수
→ 숫자 변화
→ 짧은 +점수 애니메이션

형태로 보여준다.

예:

3점
+1
4점

점수 계산 근거를 확인할 수 있는 작은 상세 영역을 제공한다.

예:

광 3
띠 5
피 11

초기 화면에서는 간단히 보여주고 터치하면 상세 내용을 펼칠 수 있도록 한다.

# 9. 고 / 스톱 UX

고/스톱 가능한 상황이 되면 플레이를 잠시 정지한다.

화면 중앙에 명확하게:

고
스톱

두 선택지를 표시한다.

점수와 현재 고 횟수도 같이 보여준다.

예:

현재 7점

[GO]
한 판 더 진행

[STOP]
7점으로 승리

사용자가 선택하기 전에는 CPU나 카드 애니메이션이 진행되지 않는다.

# 10. 특수 상황 표시

쪽

따닥

싹쓸이

폭탄

흔들기

고도리

홍단

청단

초단

광

등 중요한 상황이 발생하면 짧게 표시한다.

하지만 화면 전체를 덮는 과도한 연출은 사용하지 않는다.

게임 진행을 끊지 않는 것이 우선이다.

# 11. 정보 우선순위

화면에서 가장 중요한 순서는:

1. 내 손패
2. 바닥패
3. 현재 턴
4. 먹은 카드
5. 점수
6. 상대 상태
7. 부가 메뉴

이다.

설정이나 이벤트 UI가 카드 영역을 침범하지 않도록 한다.

# 12. 기존 UX를 기준선으로 사용하는 이유

첫 프로토타입에서는 UX 혁신을 목표로 하지 않는다.

먼저 기존 맞고 사용자들이 익숙하게 사용하는 구조를 재현한다.

그 이후 실제 플레이하면서 다음을 기록한다.

* 자주 잘못 누르는 부분
* 카드가 잘 안 보이는 부분
* 점수 이해가 어려운 부분
* 게임 흐름이 끊기는 부분
* 기다리는 시간이 긴 부분
* 불필요한 팝업
* 카드 선택 횟수
* 한 턴에 필요한 터치 수
* 신규 사용자가 이해하기 어려운 요소

# 13. UX 측정 항목

프로토타입에 간단한 디버그 로그를 넣는다.

측정:

turnDuration

cardSelectionTime

numberOfTouches

misclickCount

choiceDialogTime

animationWaitTime

gameDuration

가능하다면 개발 모드에서 콘솔 또는 Debug Panel로 확인한다.

이를 기반으로 이후 UX를 개선한다.

# 14. 차별화는 2차 단계에서 진행

1차 버전:

기존 맞고 UX와 최대한 익숙한 방식

2차 버전:

불편한 요소 제거

3차 버전:

독자적인 UX 도입

순서로 진행한다.

처음부터 기존 방식을 버리지 않는다.

# 15. 차별화 후보는 구현 후 평가

프로토타입 완성 후 다음 후보를 각각 검토한다.

A. 카드 자동 정렬

사용자가 먹을 수 있는 패를 더 빨리 찾게 할 수 있는가?

B. 매칭 카드 시각화

같은 월 카드를 약하게 연결하거나 강조하면 편한가?

C. 점수 예측

이 카드를 먹으면 예상 점수가 어떻게 바뀌는지 보여주는 것이 좋은가?

D. 초보자 모드

왜 이 패를 먹을 수 있는지 간단히 설명하는 것이 필요한가?

E. 빠른 진행

불필요한 카드 이동 애니메이션을 생략하면 게임성이 좋아지는가?

F. 한손 플레이

엄지손가락 하나만으로 대부분 플레이할 수 있는가?

G. 카드 확대

작은 모바일 화면에서도 카드 종류를 쉽게 구별할 수 있는가?

H. 현재 상황 요약

"고도리 1장 남음"

"홍단 1장 남음"

같은 정보를 제공하는 것이 게임을 더 재미있게 만드는가?

# 16. 비교 모드

가능하면 UI 설정으로 두 가지 UX를 비교할 수 있도록 한다.

CLASSIC:

기존 모바일 맞고와 유사한 UX

EXPERIMENTAL:

개선된 UX

예:

const UX_MODE = 'classic';

이렇게 설정 가능하게 한다.

게임 규칙은 동일하게 유지하고 UI/UX만 교체할 수 있어야 한다.

# 17. 구현 원칙

게임 로직과 UX를 분리한다.

게임 엔진은:

"어떤 카드가 선택되었다"
"어떤 카드가 획득되었다"
"점수가 변경되었다"

까지만 결정한다.

UI에서는:

* 어디에 표시할지
* 어떤 애니메이션을 사용할지
* 어떤 정보를 강조할지

를 결정한다.

이렇게 해야 이후 기존 UX와 새로운 UX를 쉽게 비교할 수 있다.

# 최종 목표

첫 프로토타입의 성공 기준은

"새롭다"

가 아니다.

"기존 맞고를 하던 사람이 처음 실행했을 때 아무 설명 없이 바로 플레이할 수 있다"

이다.

그 상태를 먼저 만든다.

그 다음 실제 플레이 결과를 기준으로:

유지할 UX
제거할 UX
단순화할 UX
새롭게 만들 UX

를 구분한다.

차별화는 추측으로 정하지 않고 프로토타입 플레이 결과에서 찾는다.



새로운 모바일 화투 게임 프로토타입을 만든다.

Three.js를 사용한다.

목표는 단순한 카드게임 샘플이 아니라 실제 모바일 맞고 게임처럼 처음 실행했을 때 바로 한 판 플레이할 수 있는 수준의 프로토타입이다.

향후 토스 미니앱에 올리는 것을 전제로 한다.

첫 번째 버전에서는 독창적인 UX를 억지로 만들지 않는다.

기존 한국 모바일 맞고 게임에서 오랫동안 사용된 공통적인 화면 구성, 정보 배치, 카드 진행 방식, 애니메이션 흐름을 적극적으로 참고한다.

먼저 익숙한 맞고 경험을 최대한 완성도 있게 구현한다.

그 이후 직접 플레이하며 불편한 부분과 차별화 가능한 부분을 찾는다.

특정 상용 게임 하나의 그래픽, UI, 아이콘, 효과음, 문구를 그대로 복제하지 않는다.

게임 규칙과 보편적인 UX 패턴은 참고하되 그래픽 자산과 세부 디자인은 독자적으로 제작한다.

# 핵심 목표

사용자가 기존 맞고 게임을 해본 사람이라면 별도의 튜토리얼 없이 바로 플레이 방법을 이해해야 한다.

화면을 보자마자 다음을 알 수 있어야 한다.

* 내가 가진 패
* 상대가 가진 패의 수
* 바닥에 놓인 패
* 내가 먹은 패
* 상대가 먹은 패
* 현재 점수
* 현재 누구 차례인지
* 어떤 카드를 선택할 수 있는지
* 지금 무엇을 선택해야 하는지

게임의 모든 UX는 이 원칙을 우선한다.

# 게임 모드

첫 프로토타입은 2인 맞고로 만든다.

Player 1:
실제 사용자

Player 2:
CPU

하지만 내부 구조는 players 배열을 기반으로 설계한다.

향후 다음 확장이 가능해야 한다.

* 2인 PvP
* 온라인 대전
* 3인 고스톱
* AI 난이도
* 관전자

첫 버전에서는 네트워크 멀티플레이를 구현하지 않는다.

# 기술

사용:

* TypeScript
* Three.js
* Vite
* HTML
* CSS

가능하면 React는 사용하지 않는다.

게임 테이블과 카드는 Three.js로 표현한다.

텍스트, 버튼, 메뉴, 점수, 팝업 등은 HTML/CSS Overlay를 사용한다.

모든 UI를 WebGL 안에서 구현하려 하지 않는다.

# 화면 비율

기본은 모바일 세로 화면.

기준:

390 × 844

하지만 특정 해상도에 고정하지 않는다.

Safe Area를 고려한다.

화면이 길거나 짧아져도:

* 내 손패
* 바닥패
* 상대 영역

이 겹치지 않아야 한다.

# 전체 화면 구성

화면은 크게 5개 영역으로 나눈다.

## A. 상대 영역

화면 가장 위.

표시:

* 프로필
* 이름
* 현재 점수
* 고 횟수
* 상대 손패
* 획득패

상대 손패는 뒷면으로 표시한다.

상대가 가진 카드 수를 눈으로 바로 파악할 수 있도록 겹쳐서 정렬한다.

## B. 상대 획득패

상대 영역 바로 아래 또는 좌우 공간을 활용한다.

다음 그룹으로 분리한다.

* 광
* 열끗
* 띠
* 피

카드는 모두 펼치지 않는다.

종류별로 겹쳐서 정리한다.

필요하면 숫자를 함께 표시한다.

## C. 바닥패

화면 중앙에서 가장 중요한 영역.

바닥패를 표시한다.

카드는 완전한 규칙적 Grid처럼 보이지 않도록 약간씩 위치와 회전을 달리한다.

그러나 실제 터치 가능 영역은 명확해야 한다.

카드가 너무 겹쳐서 월을 구분하기 어려워지면 안 된다.

게임에서 가장 자주 보는 영역이므로 시각적 우선순위를 높게 둔다.

## D. 내 획득패

바닥 아래.

광 / 열끗 / 띠 / 피로 분리한다.

내가 현재 어떤 족보를 만들고 있는지 쉽게 알 수 있어야 한다.

획득패가 늘어나도 내 손패 공간을 침범하지 않는다.

## E. 내 손패

화면 가장 아래.

가장 중요하다.

내 손패는 다른 어떤 UI보다 명확하게 보여야 한다.

카드가 10장일 때 한 화면에 모두 들어가야 한다.

필요하면 약간씩 겹친다.

카드 크기는 바닥패보다 약간 크게 할 수 있다.

# 카메라

완전한 Top View는 피한다.

약간 비스듬히 내려다보는 형태로 만든다.

다만 실제 3D 원근감을 과하게 사용하지 않는다.

목표는:

"실제 테이블 위 카드를 보는 느낌"

이다.

OrthographicCamera 또는 원근이 매우 약한 PerspectiveCamera를 검토한다.

# 카드 표현

화투패는 얇은 BoxGeometry 또는 PlaneGeometry를 사용한다.

카드에는 다음 정도의 입체감만 준다.

* 아주 얇은 두께
* 약한 그림자
* 미세한 회전
* 카드가 테이블에서 살짝 떠 있는 느낌

과도한 PBR이나 반사는 사용하지 않는다.

카드 그림이 가장 잘 보여야 한다.

# 카드 디자인

48장의 화투 카드.

12개월 × 4장.

각 카드에는 고유 ID를 준다.

예:

month
category
subType
isDoublePi
isSpecial

등.

게임 로직은 카드 이미지 이름에 의존하지 않는다.

# 게임 시작

게임이 시작되면 빈 테이블부터 보여주지 않는다.

짧은 셔플 또는 배분 연출 후 바로 게임 상태가 완성된다.

카드가 다음 순서로 빠르게 분배된다.

상대 손패
→ 바닥
→ 내 손패

실제 게임보다 지나치게 오래 기다리지 않게 한다.

전체 배분 애니메이션은 빠르게 진행한다.

# 기본 턴

사용자 턴의 기본 흐름은 항상 동일하다.

1. 내 손패에서 카드 선택
2. 선택한 카드가 앞으로 나옴
3. 바닥으로 이동
4. 같은 월 카드 탐색
5. 매칭
6. 획득 또는 바닥 유지
7. 더미에서 카드 한 장 뒤집기
8. 뒤집은 카드 매칭
9. 획득 처리
10. 점수 재계산
11. 특수 이벤트 확인
12. 고/스톱 확인
13. 상대 턴

이 과정이 시각적으로 끊기지 않아야 한다.

# 카드 선택

내 카드 위에 손가락을 올리거나 터치하면 즉시 반응해야 한다.

선택된 카드는:

* 약간 위로 올라온다.
* 약간 커진다.
* 다른 카드보다 앞으로 나온다.

중 하나 이상을 적용한다.

선택 상태와 실제 플레이 상태를 구분한다.

잘못 터치했을 때 카드가 바로 나가버리는 UX가 불편하다면:

첫 터치 = 선택
두 번째 터치 = 확정

방식을 지원한다.

단 UX_MODE에 따라 한 번 터치 즉시 플레이도 비교할 수 있게 만든다.

# 낸 카드

카드를 내면 손패에서 바닥으로 직선 순간 이동하지 않는다.

약 150~250ms 정도로 중앙까지 이동한다.

약간의 ease-out을 사용한다.

사용자가 자신이 어떤 카드를 냈는지 따라갈 수 있어야 한다.

# 같은 월이 없는 경우

낸 카드를 바닥에 놓는다.

큰 효과는 없다.

카드가 바닥에 정착하는 작은 움직임만 준다.

# 같은 월 한 장

두 장이 잠시 강조된다.

약 100~200ms 후 서로 가까워진다.

그 뒤 내 획득패 쪽으로 이동한다.

# 같은 월 두 장

게임을 잠시 멈춘다.

먹을 수 있는 두 카드를 강조한다.

다른 카드는 약간 어둡게 해도 된다.

사용자가 원하는 카드를 직접 선택한다.

선택을 잘못할 가능성이 없도록 터치 영역을 충분히 크게 잡는다.

# 같은 월 세 장

일반적인 맞고 규칙에 따라 처리한다.

이런 특수 상황은 게임 엔진에서 결정하고 UI는 결과를 표현한다.

# 더미 카드

더미는 중앙 바닥패 영역의 한쪽에 둔다.

내 카드 처리가 끝나면 자동으로 한 장을 뒤집는다.

연출:

더미
→ 앞으로 약간 이동
→ 카드 Flip
→ 잠깐 표시
→ 바닥 매칭

뒤집힌 카드가 너무 빨리 사라지지 않도록 한다.

사용자가 어떤 카드가 나왔는지 볼 수 있어야 한다.

# 획득 애니메이션

카드를 먹으면:

바닥
→ 서로 모임
→ 획득한 플레이어 방향으로 이동
→ 해당 획득패 그룹에 합류

한다.

모든 획득 애니메이션을 길게 하지 않는다.

150~350ms 범위 중심.

게임 전체 템포가 빠르게 유지되어야 한다.

# CPU 턴

CPU는 사용자 턴과 동일한 규칙을 따른다.

CPU가 즉시 카드를 내면 기계적으로 느껴질 수 있으므로 약간의 지연을 넣는다.

약:

400~800ms

CPU가 카드를 냄
→ 바닥 이동
→ 더미 뒤집기
→ 획득

과정은 사용자도 볼 수 있어야 한다.

CPU 플레이를 지나치게 빨리 생략하지 않는다.

# CPU 전략

첫 버전에서는 복잡한 AI를 만들지 않는다.

우선순위 기반.

예:

* 즉시 점수 획득 가능
* 광 획득
* 족보 완성
* 띠 조합
* 열끗
* 피
* 상대 견제
* 랜덤

CPU 판단과 게임 규칙을 분리한다.

# 점수

점수는 항상 보인다.

내 점수와 상대 점수를 각각 표시한다.

점수가 올라가면 단순히 숫자가 바뀌지 않는다.

예:

5
+1
6

처럼 짧게 변화 원인을 보여준다.

# 족보 정보

사용자가 획득한 카드에서 다음을 확인할 수 있어야 한다.

* 광
* 열끗
* 띠
* 피

특별 조합:

* 삼광
* 비삼광
* 사광
* 오광
* 고도리
* 홍단
* 청단
* 초단

등을 점수 엔진에서 계산한다.

# 고 / 스톱

점수 조건이 충족되면 게임 진행을 잠시 멈춘다.

중앙 또는 하단 가까운 곳에:

[고]
[스톱]

을 크게 표시한다.

동시에 다음 정보도 보여준다.

* 현재 점수
* 현재 고 횟수
* 예상 종료 점수

선택하기 전까지 다른 입력은 받지 않는다.

# 게임 종료

스톱 또는 다른 종료 조건이 발생하면:

카드 이동을 모두 끝낸 후 결과 화면을 띄운다.

표시:

승 / 패
최종 점수
고 횟수
주요 족보
특수 배수

버튼:

다시하기
메인으로

# 특수 규칙

기본 게임이 완성된 뒤 추가한다.

지원 후보:

* 쪽
* 따닥
* 싹쓸이
* 폭탄
* 흔들기
* 총통
* 피박
* 광박
* 고박
* 나가리

서비스마다 달라질 수 있는 부분은 RuleConfig로 관리한다.

특수 규칙을 추측으로 구현하지 않는다.

정확한 규칙 정의가 없으면 TODO로 남기고 기본 게임을 우선 완성한다.

# 시각 효과

화려함보다 정보 전달 우선.

사용 가능한 효과:

* 카드 짧은 Glow
* 카드 상승
* 작은 Scale
* 짧은 Particle
* 점수 Floating Text
* 약한 Screen Shake

Screen Shake는 정말 강한 이벤트에서만 사용한다.

일반 카드 획득마다 사용하지 않는다.

# 사운드

카드 놓는 소리

카드 먹는 소리

점수 발생

고

스톱

승리

패배

정도로 나눈다.

사운드 ON/OFF 가능.

앱이 백그라운드로 가면 즉시 정지한다.

# 게임 속도

전체 게임은 빠르게 진행되어야 한다.

일반 행동은:

100~350ms

강조가 필요한 행동:

500~900ms

수준으로 제한한다.

1초 이상의 연출을 반복적으로 사용하지 않는다.

# 터치 UX

모바일 기준.

Mouse Hover에 의존하지 않는다.

Raycaster 사용.

터치 영역은 카드 Mesh보다 약간 크게 설정할 수 있다.

애니메이션 중 중복 입력 금지.

InputLock을 사용한다.

단 필요한 선택 UI까지 모두 잠가버리지 않는다.

# 랜덤 Seed

동일 Seed이면 동일 초기 패가 나와야 한다.

예:

?seed=12345

URL로도 테스트할 수 있게 한다.

# UX 기록

이 프로토타입의 목적 중 하나는 이후 차별화 포인트를 찾는 것이다.

따라서 다음 데이터를 개발 모드에서 기록한다.

* 한 턴 평균 시간
* 카드 선택 시간
* 카드 선택 터치 수
* 동일 월 선택창 체류 시간
* 고/스톱 판단 시간
* 한 게임 총 시간
* 재선택 횟수

추후 Classic UX와 Experimental UX를 비교하는 데 사용할 수 있도록 한다.

# CLASSIC UX

첫 버전은 CLASSIC 모드를 기본으로 한다.

목적:

기존 맞고 사용자에게 매우 익숙한 플레이 경험.

UI의 정보 구조와 카드 움직임은 기존 모바일 맞고에서 보편적으로 사용되는 형태를 참고한다.

# EXPERIMENTAL UX

코드 구조상 이후 다음 기능을 추가할 수 있어야 한다.

* 같은 월 카드 자동 강조
* 먹을 수 있는 패 연결 표시
* 완성 직전 족보 표시
* 점수 증가 예상
* 초보자 힌트
* 빠른 플레이 모드
* 한손 모드

# 그래픽 방향

전통적인 모바일 맞고 게임의 가독성은 참고한다.

그러나 전체 분위기는 조금 더 현대적인 테이블 게임으로 만든다.

카드 자체가 가장 높은 시각적 우선순위를 가진다.

배경과 장식이 카드를 방해하지 않는다.

프로토타입에서는 지나치게 강한 캐릭터나 테마를 넣지 않는다.

향후 차별화 단계에서 테마를 변경할 수 있도록 한다.

# 최종 성공 기준

좋은 결과는 Three.js가 화려하게 보이는 것이 아니다.

실제로 게임을 실행했을 때:

* 화투를 아는 사람은 바로 플레이할 수 있고
* 내가 무엇을 냈는지 보이며
* 무엇을 먹었는지 알 수 있고
* 왜 점수가 올라갔는지 이해할 수 있고
* CPU와 자연스럽게 턴을 주고받으며
* 한 게임이 처음부터 끝까지 오류 없이 끝나는 것

이 먼저다.

첫 번째 프로토타입은 기존 모바일 맞고의 익숙함을 기준선으로 완성한다.

차별화 아이디어는 이 기준선이 완성된 후 비교 검토한다.





추가로 고려할 것은 꽤 많습니다. 지금 프롬프트는 “플레이 가능한 맞고”까지는 잘 잡혀 있는데, **프로토타입 이후 실제 서비스 후보를 만들려면 운영·규칙 경계·입력 안정성·재접속·접근성·검수 대응**이 더 필요합니다.

가장 중요한 추가 항목은 아래입니다.

* **룰 기준 명확화**

  * 맞고는 서비스마다 세부 규칙이 다를 수 있습니다.
  * 피박, 광박, 고박, 나가리, 폭탄, 흔들기, 총통, 3고 이후 배수 등을 `RulePreset`으로 분리하는 게 좋습니다.
  * “일반적인 맞고 규칙”이라고만 쓰면 AI가 임의 해석할 가능성이 큽니다.

* **초기 패 예외 처리**

  * 총통, 같은 월 4장, 바닥에 특정 월이 몰리는 경우 등 시작 직후 예외가 있습니다.
  * 배분 직후 `validateInitialDeal()` 같은 검증 단계를 명시하는 게 좋습니다.

* **턴 중간 상태 복구**

  * 모바일에서는 앱이 잠깐 백그라운드로 가거나 WebView가 중단될 수 있습니다.
  * 최소한 현재 `GameState`를 직렬화 가능하게 만들어야 합니다.
  * 다시 들어왔을 때 “처음부터”가 아니라 현재 판을 복구할 수 있게 설계하는 것이 좋습니다.

* **애니메이션과 실제 상태 분리**

  * 카드가 화면상 이동 중이어도 논리 상태가 꼬이면 안 됩니다.
  * `logicalState`와 `visualState`를 분리하고, 애니메이션 실패 시에도 게임 상태는 복구 가능해야 합니다.
  * 이 부분은 카드게임에서 버그가 많이 나는 지점입니다.

* **입력 중복 방지**

  * 더블탭
  * 빠른 연속 탭
  * 애니메이션 중 다른 카드 터치
  * 팝업 뜨는 순간 카드 터치
  * 화면 전환 도중 입력
    이런 케이스를 별도로 테스트해야 합니다.

* **CPU 공정성**

  * CPU가 사용자 패나 더미 순서를 알고 판단하면 안 됩니다.
  * AI는 공개된 정보만 보고 판단하도록 제한해야 합니다.
  * 디버그용 정보와 CPU 판단용 정보도 분리하는 게 좋습니다.

* **게임 속도 옵션**

  * 일반
  * 빠르게
    정도는 초기에 구조를 열어두는 게 좋습니다.
  * 애니메이션 시간을 하드코딩하지 말고 `GameSpeedConfig`로 분리하세요.

* **카드 가독성**

  * 작은 화면에서 화투 카드 그림이 생각보다 빨리 뭉개집니다.
  * 카드 텍스처 해상도, mipmap, anisotropy, pixel ratio, 확대 시 선명도 등을 테스트해야 합니다.
  * 특히 390px 폭 기준에서 손패 10장이 얼마나 읽히는지 실제 확인이 필요합니다.

* **손가락 가림 문제**

  * 모바일에서는 누르는 순간 손가락이 카드와 바닥패를 가립니다.
  * 선택 카드가 위로 튀어나오거나, 확대 Preview를 잠깐 띄우는 방식이 유용할 수 있습니다.

* **한손 플레이**

  * 토스 안에서 짧게 플레이할 가능성을 생각하면 중요합니다.
  * 주요 인터랙션을 화면 하단 60~70% 안에 넣는 방식도 검토할 만합니다.

* **튜토리얼이 없어도 되는지 검증**

  * 화투를 아는 사용자만 보면 문제없지만 신규 사용자 유입을 생각하면 별개입니다.
  * 첫 1판만 “먹을 수 있는 패 강조” 정도의 최소 안내를 넣는 구조를 열어두면 좋습니다.

* **초보자 모드와 일반 모드 분리**

  * 초보자: 같은 월 강조, 점수 조합 설명
  * 일반: 최소 UI
  * 둘을 섞으면 숙련자에게 번거로울 수 있습니다.

* **정보 과부하 방지**

  * 점수, 족보, 획득패, 고 횟수, 상대 상태를 다 띄우면 화면이 복잡해집니다.
  * 기본 HUD와 상세 정보 패널을 분리하세요.

* **결과 화면 분석**

  * 단순히 승/패만 보여주지 말고
  * 어떤 조합으로 몇 점
  * 어떤 배수
  * 최종 점수
    를 단계별로 보여주면 사용자가 결과를 납득하기 쉽습니다.

* **리플레이 가능성**

  * Seed만 저장하는 것보다 행동 로그도 저장하는 게 좋습니다.
  * 예:
    `turn 12 / player played 3월 띠 / draw 7월 피`
  * 버그 재현과 밸런스 분석에 매우 유용합니다.

* **게임 로그 포맷**

  * 단순 콘솔 로그보다 구조화된 이벤트 로그가 좋습니다.
  * 나중에 실제 유저 행동 분석에도 재사용할 수 있습니다.

* **자동 테스트**

  * 게임 한 판을 수천 번 CPU vs CPU로 돌려서

    * 무한 루프
    * 카드 중복
    * 카드 유실
    * 종료 안 됨
    * 점수 음수
      등을 자동 검증하는 테스트를 넣으면 좋습니다.

특히 저는 아래 5가지는 지금 프롬프트에 반드시 추가하겠습니다.

1. **RulePreset**
2. **Save/Restore 가능한 GameState**
3. **논리 상태와 애니메이션 상태 분리**
4. **CPU는 공개 정보만 사용**
5. **CPU vs CPU 자동 시뮬레이션 테스트**

그리고 차별화 관점에서도 한 가지 더 봐야 합니다.

기존 맞고는 대부분 **“카드를 잘 치는 경험”**에 집중돼 있습니다. 그래서 차별화 후보를 찾을 때는 그래픽보다 아래를 비교하는 게 더 중요합니다.

**판단 부담을 줄이는 게임**

* 먹을 수 있는 월 강조
* 족보 진행률
* 위험 패 표시

**속도를 극단적으로 빠르게 한 게임**

* 1탭 플레이
* 애니메이션 축약
* 3~5분 한 판

**보는 재미를 강화한 게임**

* 카드 충돌
* 족보 완성 연출
* 3D 테이블

**초보자 친화 게임**

* 왜 이 카드를 먹었는지 표시
* 점수 생성 이유 표시
* 실수 방지

**전략성을 강화한 게임**

* 상대 획득패 분석
* 남은 카드 추정
* 조합 위험도

이 5개는 서로 방향이 꽤 다르기 때문에, 프로토타입이 완성된 뒤 **CLASSIC을 기준군으로 두고 각각 하나씩 EXPERIMENTAL 버전으로 비교**하면 차별점 찾기가 좋습니다.

다음 프롬프트에는 아예 `게임 규칙 명세`, `화면 좌표 명세`, `애니메이션 명세`, `예외상황 명세`, `테스트 명세`까지 묶는 게 좋습니다. 그러면 현재 기차 디펜스 프롬프트보다도 훨씬 덜 모호한 개발 지시서가 됩니다.




더 고려한다면, 이제는 **게임 구현 자체보다 “실제 서비스로 갔을 때 문제될 영역”**까지 봐야 합니다.

특히 추가할 만한 것은 다음입니다.

* **세션 길이 설계**

  * 한 판 평균 몇 분인지
  * 토스에서 잠깐 들어와 플레이하기에 적당한지
  * 너무 길면 중간 저장이나 빠른 모드가 필요합니다.

* **재진입 UX**

  * 앱을 나갔다 돌아왔을 때
  * 진행 중인 판 복구
  * 결과 화면 복구
  * 네트워크 끊김 후 상태 복구
    를 구분해야 합니다.

* **네트워크 멀티플레이 대비**

  * 지금은 CPU전이어도 나중에 PvP를 하려면
  * `게임 결과를 클라이언트가 결정하는 구조`는 피하는 게 좋습니다.
  * 초기부터 Action 기반으로 설계하면 전환이 쉽습니다.
  * 예: `PLAY_CARD`, `SELECT_CAPTURE`, `GO`, `STOP`

* **결정적 시뮬레이션**

  * 같은 Seed + 같은 Action 순서라면 항상 같은 결과가 나와야 합니다.
  * 리플레이, 서버 검증, 버그 재현 모두 쉬워집니다.

* **Undo를 넣지 않을 것인지**

  * 일반 맞고에서는 패를 낸 뒤 취소를 허용하지 않는 편이 자연스럽습니다.
  * 대신 실수 방지를 위해 `선택 → 확정` 옵션을 둘 수 있습니다.
  * 이 정책을 명확하게 정해야 UX가 흔들리지 않습니다.

* **빠른 플레이와 연출의 충돌**

  * 처음에는 카드 애니메이션이 재미있어도 반복하면 느리게 느껴질 수 있습니다.
  * `NORMAL / FAST`를 구조적으로 분리하는 게 좋습니다.

* **중요 이벤트 우선순위**

  * 고도리, 홍단, 광, 폭탄 등이 연속 발생하면 효과가 겹칠 수 있습니다.
  * `AnimationQueue` 또는 `EventPresentationQueue`가 필요합니다.
  * 동시에 여러 팝업이 뜨지 않도록 해야 합니다.

* **카드 이동 경로 충돌**

  * 여러 장을 획득할 때 카드가 겹치며 날아가면 무엇을 먹었는지 안 보입니다.
  * 다중 카드 이동 시 약간의 시간차를 둘 필요가 있습니다.

* **정보 공개 수준**

  * 남은 패 수를 어디까지 보여줄 것인지
  * 상대의 광/띠/피 개수를 얼마나 명확하게 보여줄 것인지
  * 족보 완성 직전 상태를 알려줄 것인지
    를 정해야 합니다.
  * 이건 단순 UI가 아니라 게임 난이도에 영향을 줍니다.

* **초보자 도움의 경계**

  * “같은 월 카드 강조”는 편의 기능
  * “가장 좋은 패 추천”은 사실상 AI 조언
    입니다.
  * 둘은 플레이 경험이 크게 달라지므로 분리해야 합니다.

* **CPU 캐릭터성**

  * AI 강도만 바꾸는 것보다 플레이 성향을 나누는 것도 좋습니다.
  * 공격형
  * 안정형
  * 고를 자주 하는 형
  * 빠르게 스톱하는 형
  * 피 위주
  * 족보 위주
    같은 식입니다.
  * 동일 룰인데도 게임 반복성이 좋아집니다.

* **CPU 난이도 조절 방법**

  * 단순히 “쉬움은 랜덤”으로 하지 않는 것이 좋습니다.
  * 탐색 정보량이나 선택 평가 정확도를 낮추는 방식이 자연스럽습니다.

* **첫 판 경험**

  * 첫 게임부터 아주 불리한 패가 나오거나 CPU가 압도하면 이탈할 수 있습니다.
  * 반대로 결과를 조작하면 공정성 문제가 생깁니다.
  * 튜토리얼 판과 일반 판을 명시적으로 분리하는 게 낫습니다.

* **게임 시작 속도**

  * 로고
  * 로딩
  * 메뉴
  * 매칭
  * 배분
    이 길어지면 실제 플레이 전에 피로해집니다.
  * “앱 실행 → 첫 카드 선택 가능” 시간을 별도로 측정할 가치가 있습니다.

* **화면 전환 최소화**

  * 메인 → 게임 → 결과 → 메인처럼 여러 화면을 오가기보다
  * 실제 게임을 중심으로 UI를 단순하게 유지하는 것이 좋습니다.

* **세로 화면에서의 하단 시스템 UI**

  * 브라우저/WebView의 하단 영역이나 Safe Area가 손패를 침범하지 않는지 확인해야 합니다.
  * 손패는 화면 최하단에 딱 붙이지 않는 게 좋습니다.

* **카드 이미지 제작 파이프라인**

  * 48장 이미지를 개별 텍스처로 관리할지
  * Texture Atlas로 묶을지
  * WebP/AVIF를 사용할지
    미리 결정하면 성능이 달라집니다.
  * Three.js라면 Atlas도 검토할 만합니다.

* **텍스처 로딩 실패**

  * 일부 카드 이미지가 실패해도 게임 자체가 멈추면 안 됩니다.
  * fallback 카드가 필요합니다.

* **디바이스 성능 등급**

  * 고급폰과 저사양폰에서 같은 효과를 강제할 필요가 없습니다.
  * LOW / NORMAL 그래픽 레벨 정도는 내부적으로 둘 수 있습니다.

* **프레임 드랍 대응**

  * 애니메이션 로직을 frame count 기반으로 작성하지 말고 elapsed time 기반으로 해야 합니다.
  * 60fps와 30fps에서도 결과가 같아야 합니다.

* **화면 크기 극단값**

  * 아주 작은 Android
  * 긴 화면
  * 폴더블
  * 태블릿
    등을 최소한 레이아웃 계산 구조상 대응하도록 해야 합니다.

* **접근성**

  * 색상만으로 선택 상태를 표시하지 않기
  * 카드 선택 시 위치/크기 변화 병행
  * 효과음 없이도 상태를 이해할 수 있게 하기
  * 작은 텍스트 남용하지 않기
    정도는 초기부터 넣는 것이 좋습니다.

그리고 서비스 관점에서 가장 중요하게 추가할 것은 **경제 요소를 게임 엔진과 완전히 분리하는 것**입니다.

예를 들어 나중에 보상이나 재화가 들어가더라도:

`HwatuGameEngine → 승패와 점수만 계산`

`RewardSystem → 결과를 받아 보상 계산`

구조로 두는 것이 좋습니다.

게임 로직 안에 `coin += 100` 같은 것을 넣지 않는 게 좋습니다. 토스 배포나 서비스 정책 검토 과정에서도 이런 분리가 유리합니다.

제가 지금 단계에서 가장 관심 있게 볼 추가 항목은 따로 있습니다.

### 1. Action Log

게임 전체를 다음처럼 저장합니다.

```text
DEAL seed=83625
P1 PLAY 3-2
P1 CAPTURE 3-1
DRAW 7-3
NO_MATCH
P2 PLAY 5-1
...
P1 GO
...
P1 STOP
```

이것 하나로 **버그 재현 + 리플레이 + 서버 검증 + AI 학습 데이터 + UX 분석**까지 연결됩니다.

### 2. 완전 자동 플레이

`CPU vs CPU`를 화면 없이 실행할 수 있게 합니다.

```text
simulateGames(100000)
```

그리고 확인:

```text
평균 턴 수
평균 플레이 시간 추정
선공 승률
후공 승률
GO 횟수
나가리 비율
각 족보 발생률
비정상 종료
48장 invariant 위반
```

이 기능은 상당히 가치가 큽니다.

### 3. UI와 게임 진행 속도의 완전 분리

예를 들어:

```ts
game.playCard(cardId)
```

결과:

```ts
[
  CARD_PLAYED,
  CARD_MATCHED,
  CARD_CAPTURED,
  SCORE_CHANGED
]
```

UI가 이것을 1초에 보여주든 0.2초에 보여주든 **게임 결과는 동일**해야 합니다.

이렇게 해놓으면 나중에:

* 일반 모드
* 초고속 모드
* 리플레이
* 관전
* 서버 시뮬레이션

을 거의 같은 엔진으로 처리할 수 있습니다.

### 4. 처음부터 비교 가능한 UX

이건 이번 프로젝트 목적과 특히 잘 맞습니다.

```ts
UX_MODE = CLASSIC
UX_MODE = ASSISTED
UX_MODE = FAST
UX_MODE = EXPERIMENTAL
```

정도로 두고 동일한 게임 엔진 위에서 비교합니다.

그러면 나중에 “뭐가 더 좋은 것 같다”가 아니라,

```text
CLASSIC
평균 턴 선택: 2.3초
평균 터치: 1.7회

ASSISTED
평균 턴 선택: 1.5초
평균 터치: 1.2회
```

처럼 판단할 수 있습니다.

### 5. 가장 중요한 질문 하나

프로토타입을 만들고 나서 결국 확인해야 할 것은:

**“기존 맞고에서 무엇을 그대로 유지해야 하고, 무엇은 단지 오래돼서 남아 있는 UX인가?”**

입니다.

예를 들어 `같은 월 두 장 중 하나를 직접 고르는 행위`는 게임의 중요한 판단일 수 있지만, `먹은 패를 아주 작게 겹쳐 놓는 방식`은 단순히 작은 모바일 화면 때문에 생긴 관습일 수도 있습니다.

그래서 저는 이번 프로젝트를 단순한 화투 구현보다는 **“기존 맞고 UX의 기준 모델을 먼저 만든 다음 하나씩 제거·대체해 보는 프로토타입”**으로 잡는 것이 가장 흥미롭다고 봅니다.

다음 단계에서는 지금까지 나온 내용을 하나로 합쳐서 **Codex/Claude Code에 그대로 넣을 수 있는 최종 마스터 프롬프트**로 정리하면 됩니다. 그 버전에는 `룰 → 화면 → UX → 상태머신 → Three.js → 테스트 → 자동 시뮬레이션 → 차별화 실험`까지 한 번에 포함시키는 게 좋습니다.


추가로 충분히 확장해보면, 이제는 단순 구현 체크리스트를 넘어서 **게임 구조·UX·룰 안정성·운영·데이터·실험·서비스 확장성**까지 함께 봐야 합니다.

아래 정도까지 고려해두면 프로토타입 이후 다시 구조를 갈아엎을 가능성이 많이 줄어듭니다.

* **규칙 엔진의 독립성**

  * 렌더링 없이도 한 판이 끝까지 진행되어야 함
  * Three.js가 없어도 룰 테스트가 가능해야 함
  * 게임 결과는 UI가 아니라 GameEngine이 결정
  * 점수 계산과 턴 진행도 별도 모듈
  * 룰 변경 시 화면 코드를 건드리지 않도록 설계

* **RulePreset 구조**

  * 서비스마다 다른 맞고 세부 규칙을 preset으로 관리
  * `standard`
  * `fast`
  * `beginner`
  * `custom`
  * 같은 구조 가능
  * 각 룰의 기본값과 변경 가능 범위를 명시
  * 게임 도중 preset 변경 금지

* **규칙 버전**

  * 나중에 룰이 변경되면 이전 플레이 기록을 재현할 수 있도록 `ruleVersion` 저장
  * 예:
    `ruleVersion: "1.0.0"`

* **카드 데이터 검증**

  * 48장 중복 없음
  * 월별 4장
  * 카테고리 정확성
  * 쌍피 여부
  * 특수패 여부
  * 카드 정의를 실행 시 자동 검사

* **초기 분배 검증**

  * 분배 직후 특수 상황 확인
  * 초기 패 재분배가 필요한 규칙이 있다면 별도 처리
  * 패를 다시 섞을 때 Seed 처리도 명확히

* **선공 결정**

  * 첫 판 선공 규칙
  * 다음 판 선공 규칙
  * 승자가 선공인지
  * 번갈아 하는지
  * 랜덤인지
  * 서비스 룰로 분리

* **동률 처리**

  * 점수가 같을 때
  * 게임 종료 조건 충돌
  * 동시에 여러 족보 완성
  * 고 선언 직후 상대 점수 조건 달성
  * 이런 edge case를 명시

* **나가리 처리**

  * 단순 무승부인지
  * 다음 판 배수와 연결되는지
  * 프로토타입에선 다음 판 이월을 구현할지
  * 명확하게 분리

* **배수 체계**

  * 점수와 배수를 따로 계산
  * 기본 점수
  * 고 배수
  * 피박
  * 광박
  * 고박
  * 흔들기
  * 폭탄
    등을 하나의 숫자로 바로 계산하지 말고 breakdown 제공

* **결과 계산 설명 가능성**

  * 최종 점수만 반환하지 말고
  * `baseScore`
  * `multipliers`
  * `bonuses`
  * `penalties`
  * `finalScore`
    반환
  * 결과 화면과 디버깅에 유용

* **게임 Action 중심 설계**

  * 모든 사용자 행동을 Action으로 정의
  * `PLAY_CARD`
  * `SELECT_CAPTURE`
  * `DECLARE_GO`
  * `DECLARE_STOP`
  * `CONFIRM`
  * 향후 멀티플레이와 replay가 쉬워짐

* **Command와 Event 분리**

  * Command = 사용자가 요청한 것
  * Event = 게임에서 실제 발생한 결과
  * 예:
    `PLAY_CARD(3-1)`
    →
    `CARD_PLAYED`
    `MATCH_FOUND`
    `CARD_CAPTURED`

* **완전 deterministic하게 만들기**

  * Seed + RuleVersion + ActionLog가 같으면 동일 결과
  * Random을 직접 `Math.random()`으로 호출하지 않기
  * RNG 모듈 하나를 통해서만 접근

* **GameState 직렬화**

  * JSON 형태로 저장 가능
  * DOM
  * Mesh
  * Texture
  * 함수
    를 GameState 안에 넣지 않음

* **저장 시점**

  * 매 턴 종료
  * 고/스톱 선택 직전
  * 게임 종료
    정도를 checkpoint로 둘 수 있음

* **강제 종료 복구**

  * 앱 강제 종료
  * 전화 수신
  * 화면 잠금
  * 백그라운드 전환
  * WebView reload
    이후 복구 가능하게 설계

* **중간 상태 복구 금지 영역**

  * 카드가 이동 중일 때 저장하지 않음
  * 논리적으로 안정된 checkpoint에서만 저장
  * 또는 애니메이션 진행 상태를 저장하지 않고 완료 상태로 복구

* **AnimationQueue**

  * 여러 이벤트가 한꺼번에 발생해도 순차 표현
  * 게임 상태와 애니메이션 완료를 분리
  * 연출 Skip도 가능해야 함

* **Animation cancellation**

  * 앱이 백그라운드로 가거나 게임 종료 시 애니메이션 중단
  * Promise가 영원히 대기하지 않도록 처리
  * 모든 tween cleanup

* **애니메이션 우선순위**

  * 일반 카드 이동
  * 점수 획득
  * 족보 완성
  * 고/스톱
  * 게임 종료
    순으로 중요도 구분
  * 작은 이벤트가 큰 이벤트 연출을 막지 않게 함

* **연출 동시성 규칙**

  * 동시에 보여줘도 되는 것
  * 반드시 순차로 보여줘야 하는 것
    구분
  * 예: 점수 숫자 변화와 카드 정렬은 동시 가능

* **FAST 모드**

  * animation duration 배율
  * CPU delay
  * popup duration
  * 점수 연출
    을 개별 수정하지 않고 전체 multiplier로 조절

* **SKIP 전략**

  * 사용자가 화면을 연속 터치하면 현재 연출을 빠르게 완료
  * 상태를 건너뛰지 않고 animation만 skip

* **입력 정책**

  * 어떤 상태에서 어떤 입력이 가능한지 명시
  * 예:
    `PLAYER_SELECT` → 내 손패만
    `SELECT_CAPTURE` → 후보 바닥패만
    `GO_STOP` → 두 버튼만

* **입력 버퍼 여부**

  * 애니메이션 중 다음 카드 터치를 미리 받지 않을 것인지
  * 초기에는 버퍼링하지 않는 것이 안전

* **멀티터치**

  * 두 손가락으로 동시에 카드 눌렀을 때
  * pinch
  * scroll
    등이 카드 선택으로 오인되지 않도록 처리

* **drag 지원 여부**

  * 카드를 드래그해서 내는 UX를 나중에 실험 가능하게 구조화
  * 기본은 tap
  * drag는 별도 UX mode

* **long press**

  * 카드 확대
  * 카드 상세 보기
    등에 사용할지 검토
  * 필수 기능으로 만들지는 않음

* **터치 피드백**

  * 선택 가능
  * 선택됨
  * 비활성
  * 후보
  * 확정
    상태별 시각 표현 분리

* **손가락 가림 대응**

  * 선택 카드 위로 상승
  * 확대 프리뷰
  * 후보 카드 테두리
  * 하단 손패에 충분한 여백

* **잘못된 입력 피드백**

  * 아무 반응 없이 무시하지 말고
  * 짧은 진동/미세 shake/outline 등
  * 단, 과하지 않게

* **햅틱**

  * 카드 확정
  * 고
  * 스톱
  * 큰 족보
    정도만 선택적으로
  * 지원하지 않는 환경에서도 문제 없어야 함

* **오디오 믹싱**

  * BGM
  * 카드 SFX
  * UI SFX
    분리
  * 사용자 설정 저장

* **음성이나 효과음 중첩**

  * 카드 소리가 짧은 시간에 5개 겹치지 않도록 동시 재생 제한
  * 동일 효과음 throttling

* **접근성**

  * 색상만으로 상태 구분하지 않기
  * 밝기/크기/위치 변화 병행
  * 텍스트 최소 크기
  * 사운드 없이도 게임 가능

* **색각 이상 고려**

  * 빨강/초록만으로 후보 구분하지 않기
  * outline 형태 차이도 사용

* **폰트**

  * 숫자 가독성
  * 점수는 tabular numerals가 유리
  * 숫자 변동 시 폭이 흔들리지 않도록

* **카드 텍스처**

  * 카드 48장을 개별 텍스처로 할지 Atlas로 할지 결정
  * 첫 프로토타입은 관리 편의 우선
  * 최적화 단계에서 Atlas 고려

* **Texture preload**

  * 게임 시작 직전에 카드가 하나씩 늦게 뜨지 않도록 필요한 리소스 preload
  * 로딩 진행률 표시 필요 여부 판단

* **Texture fallback**

  * 이미지 실패 시 빈 카드 대신 placeholder 표시
  * 게임 상태는 계속 정상 진행

* **Texture dispose**

  * scene 재시작할 때 texture/material/geometry 중복 생성 방지
  * dispose 정책 명시

* **Object Pooling**

  * Floating Text
  * Particle
  * 임시 Highlight
    같은 반복 요소는 pool 검토
  * 카드 자체는 매 턴 생성/삭제하지 않기

* **렌더 루프**

  * 변화가 거의 없는 카드게임이라 항상 60fps 렌더링이 필수인지 검토
  * 애니메이션 중에는 연속 렌더
  * 정적인 상태에서는 렌더 감소도 가능

* **Delta time**

  * 초 단위 시간 기반

* **브라우저 resize**

* **전역 오류 처리**

  * 개발 모드에서는 상태 dump
  * 실제 서비스에서는 안전한 재시작 제공

* **중복 새 게임 방지**

* **로딩 실패 UX**

  * 리소스 실패 원인 표시

* **버전 호환**

* **개인정보 최소화**

  * 다시하기
  * 중도 종료

  * 버튼을 상단에 두지 않기

  * 중요한 패만 전체 연출

* **긴 게임 방지**

  * UX가 늘어지는 원인이 룰인지 애니메이션인지 구분할 수 있게 실제 logical duration과 presentation duration을 따로 기록

* **게임 종료 직전 긴장감**

  * 카드 수 감소
  * 점수 근접
  * 고 횟수
    를 시각적으로 어느 정도 표현할지 검토

* **상대 위험도 표시**

  * 초보자 편의로 제공할지
  * 전략적 재미를 훼손하는지 비교 필요

* **카운팅 지원 여부**

  * 이미 나온 월이나 카드 수를 자동으로 시각화하면 전략성이 크게 달라질 수 있음
  * 별도 실험 기능으로만

* **정보 비대칭 유지**

  * 편의 기능이 숨은 정보를 노출하지 않도록 주의

* **튜토리얼 구조**

  * 별도 긴 튜토리얼보다 첫 게임 중 필요한 순간에만 안내
  * 이미 알고 있는 사용자는 skip

* **튜토리얼 전용 게임 상태**

  * 일반 GameEngine에 튜토리얼 조건문을 마구 추가하지 않기
  * ScriptedAction 또는 TutorialController로 분리

* **첫 게임 카드 배분**

  * 조작된 쉬운 판을 제공한다면 일반 게임과 명확하게 분리
  * 실제 랜덤 게임처럼 위장하지 않기

* **게임 테마 시스템**

  * 테이블 배경
  * 카드 뒷면
  * 효과
    등을 나중에 교체 가능
  * 룰 코드와 분리

* **카드 스킨**

  * 카드 인식성이 바뀌지 않도록 월별 핵심 시각 요소 유지 여부 검토

* **브랜드 톤**

  * 카지노 느낌
  * 전통 화투 느낌
  * 캐주얼 모바일 느낌
    중 어디를 목표로 할지 나중에 비교
  * 1차 프로토타입은 중립적

* **캐릭터 추가 가능성**

  * CPU의 플레이 스타일과 캐릭터를 연결할 수 있음
  * 초기에는 게임 화면을 가리는 캐릭터 연출 피하기

* **관전 모드 대비**

  * 사용자 입력 없이 Event만 재생할 수 있으면 구현이 쉬움

* **온라인 PvP 대비**

  * 클라이언트가 직접 상태를 수정하는 구조 금지
  * Action → authoritative state transition 구조가 유리

* **네트워크 지연 대비**

  * 나중에 서버 게임으로 바뀌어도 animation이 server response와 분리될 수 있게 설계

* **Reconnect**

  * 서버 authoritative state를 받아 화면을 즉시 rebuild할 수 있는 구조
  * 모든 Mesh 상태를 incremental update에만 의존하지 않기

* **State → Render rebuild**

  * 언제든 현재 GameState 하나만으로 전체 테이블을 다시 그릴 수 있어야 함
  * 매우 중요

* **서버 검증 대비**

  * Action에 actor, turn, sequence number를 둘 수 있게
  * replay attack이나 중복 요청 방지 기반

* **Action sequence**

  * 같은 Action이 두 번 처리되지 않게 idempotency 고려

* **경제 시스템 분리**

  * 승패/점수와 포인트/보상 완전 분리
  * 프로토타입에서는 보상 없이 진행

* **게임 내 재화가 들어갈 경우**

  * RuleEngine이 돈을 알지 않게
  * `GameResult`만 외부 시스템에 전달

* **광고나 이벤트 UI**

  * 게임 진행 영역과 분리
  * 프로토타입에서는 제외하는 것이 좋음

* **중도 이탈**

  * 사용자가 게임 중 나가면
  * abandon
  * pause
  * resume
    를 구분

* **재시작**

  * 게임 중 새 게임을 누를 때 즉시 초기화할지 확인창을 둘지 UX 결정

* **결과 화면 체류**

  * 사용자가 결과를 충분히 이해할 수 있어야 하지만 지나치게 길면 안 됨

* **결과 breakdown**

  * 어떤 족보
  * 기본 점수
  * 배수
  * 최종 점수
    를 순서대로 보여주는 방식 추천

* **결과 Replay**

  * “마지막 턴 다시보기” 같은 기능도 향후 가능

* **데이터 기반 차별화**

  * 개발자가 좋아하는 기능이 아니라 실제 지표가 개선되는 기능을 남기기

* **프로토타입 폐기 기준**

  * 재미가 없음
  * 한 판이 지나치게 김
  * 카드가 작음
  * 점수가 이해되지 않음
  * 기존 맞고보다 터치가 많음
    같은 명확한 실패 기준도 마련

* **프로토타입 성공 기준**

  * 게임 규칙 완주
  * 오류 없이 반복 플레이
  * 기존 맞고 사용자 즉시 이해
  * 평균 턴 흐름이 끊기지 않음
  * 결과 점수 설명 가능
  * 저사양 모바일에서도 안정적

특히 구조적으로는 아래 8개를 **초기부터 반드시 넣는 편**을 권합니다.

1. `RuleVersion`
2. `Seeded RNG`
3. `Serializable GameState`
4. `ActionLog`
5. `State Invariant Validator`
6. `Headless CPU vs CPU Simulator`
7. `State → Full Render Rebuild`
8. `Animation과 GameState 완전 분리`

이 8개는 화면에는 전혀 보이지 않지만, 프로젝트가 조금만 커져도 가치가 크게 나타납니다.

그리고 이번 프로젝트의 핵심 차별화 실험은 그래픽보다 다음 순서로 하는 편이 좋습니다.

**1단계 — 기존 방식 그대로**
`CLASSIC`

**2단계 — 정보만 개선**
`ASSISTED`

* 같은 월 강조
* 족보 진행 표시
* 점수 발생 이유

**3단계 — 조작 단순화**
`FAST`

* 1탭
* 짧은 애니메이션
* 자동 정렬

**4단계 — 게임 판단 보조**
`SMART`

* 현재 선택의 결과 미리보기
* 위험 조합 표시
* 남은 카드 기반 정보

**5단계 — 표현 자체 차별화**
`EXPERIMENTAL`

* Three.js를 활용한 카드 깊이
* 테이블 공간감
* 카드 움직임
* 새로운 획득패 표현

이렇게 해야 나중에 **“Three.js라서 다른 맞고”가 아니라 “기존 맞고에서 불편했던 부분을 해결해서 다른 맞고”**가 됩니다.

그리고 하나 더 중요합니다. 지금 주신 기차 디펜스 프롬프트에는 세계관 때문에 자연스럽게 **“무엇이 재미인가”**가 들어 있습니다. 화투 프롬프트에도 이 문장을 명시하는 게 좋습니다.

> 이 게임의 재미는 화려한 연출이 아니라, 내가 낸 한 장이 어떤 결과를 만들었는지 즉시 이해하고 다음 선택을 빠르게 고민하는 데 있다. 모든 UI·애니메이션·보조 기능은 이 판단 흐름을 방해하지 않아야 한다.

이 한 줄을 기준으로 잡으면 이후 기능을 추가할 때도 **넣을 기능과 버릴 기능을 판단하기 훨씬 쉬워집니다.**

### 기존 맞고는 생각보다 "화면 전환"을 많이 하지 않습니다

대부분 **하나의 게임 테이블을 계속 유지하고 그 위의 상태만 바꿉니다.**

예를 들어 고/스톱도:

```text
게임 화면
→ 다른 페이지
```

가 아니라,

```text
게임 화면
+
GO/STOP Modal
```

입니다.

결과 역시 비슷합니다.

이건 우리 Three.js 구현에서도 그대로 가져갈 가치가 높습니다.

```text
Three.js Scene = 계속 유지

HTML Overlay만 변경

NORMAL
CAPTURE_SELECT
SPECIAL_EVENT
GO_STOP
RESULT
PAUSE
```

이렇게 하면 카드 Mesh를 계속 생성/파괴하지 않아도 됩니다.

## 실제 전환에서 특히 참고할 7장

프로토타입을 위해서는 스크린샷을 무작정 많이 모으기보다 아래 **7개 상태**를 실제 게임별로 비교하는 게 낫습니다.

### ① 게임 시작 직전

```text
상대 표시
↓
카드 배분 시작
```

볼 것:

* 상대 정보가 언제 나타나는지
* 게임판이 먼저 나오는지
* 카드가 먼저 배분되는지

### ② 배분 완료

```text
10장 손패
8장 바닥패
더미
```

이 화면이 사실상 **기준 레이아웃**입니다.

### ③ 카드 한 장 낸 직후

```text
내 손패
      ↓
    중앙
      ↓
   바닥패
```

Three.js에서 가장 중요하게 구현할 장면입니다.

### ④ 같은 월 2장 선택

기본 화면을 유지하면서

```text
[후보 A]  [후보 B]

나머지 화면 ↓
```

처럼 선택 가능한 카드만 강조하는 방식이 좋습니다.

### ⑤ 족보 / 특수상황 발생

예:

```text
홍단!
고도리!
쪽!
따닥!
```

전체 화면 전환보다는 짧은 연출을 겹칩니다.

### ⑥ GO / STOP

현재 실제 화면에서도 명확하게 확인되는 형태입니다.

```text
       ┌───────────┐
       │ 현재 점수 │
       │           │
       │ GO   STOP │
       └───────────┘

       게임판 유지
```

한게임의 해당 화면은 실제로 이런 구조입니다.

### ⑦ 결과

피망의 실제 화면처럼:

```text
┌──────────────────┐
│       승          │
│                  │
│    최종 획득량    │
│                  │
│ 11점 × 4배 = 44점 │
│                  │
│ 나가기      확인  │
└──────────────────┘

   기존 게임판
```

처럼 **게임의 맥락을 뒤에 남기는 방식**을 참고할 수 있습니다.

화투 프로젝트에서도 트럼프 카드를 확보해두면 의외로 쓸모가 큽니다. 제가 특히 비교할 부분은 다음입니다.

* **딜링**: 블랙잭의 카드가 한 장씩 날아가는 방식
* **카드 겹침**: 여러 장을 작은 공간에 보여주는 방식
* **뒤집기**: dealer hole card flip
* **선택 강조**: 카드 선택 시 elevation/scale
* **카드 뒷면**: 상대 패 표현
